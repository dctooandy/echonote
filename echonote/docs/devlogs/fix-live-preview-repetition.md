# 即時預覽重複迴圈 開發紀錄

分支：`fix/live-preview-repetition`
狀態：已完成（實機驗收通過、`/spec-check` 落差已處理），待併入 master

即時錄音的預覽常出現一長串重複的字，例如「經常經常經常…」「Helps,Helps,…」。這個分支在原生端定稿前、Dart 端顯示前把這種迴圈收成一次，並加上可以重播同一段錄音的 debug 工具，用來比較修正前後。正式逐字稿來自停止後的離線轉錄，不受影響。規格：[`docs/specs/fix-live-preview-repetition/`](../specs/fix-live-preview-repetition/fix-live-preview-repetition.md)。

## 目標

- 預覽不再顯示「同一段 1～10 字連續出現 4 次以上」的迴圈。
- 不能變慢：median 解碼時間增加不超過 20%，max lag 不超過 3 秒。
- 能用同一段音訊穩定重現，修正前後可以比較。

## 踩到的坑

### 一、迴圈為什麼會一直留在預覽上

**現象**：2026-10-21 量 T6 時，帶不帶詞庫的兩組預覽都有大段重複，而且不會消失。

**原因**：即時預覽為了速度關掉了 whisper 的 temperature fallback（2026-10-08 它讓延遲累積到 216 秒）。fallback 原本會在結果不可靠時重新辨識，重複迴圈正是會被它丟掉的那種結果，關掉之後就沒有東西擋住迴圈。原生端每 15 秒把視窗的文字直接接到已定稿文字後面（`committed += text`），沒有任何檢查，所以一旦在定稿那一刻陷入迴圈，迴圈就永久留下。實際錄音約 3 分半，原生端在定稿時收掉了 3 個迴圈，證實這個推論。

**修法**：兩層都收合，規則相同。原生端在定稿前，連同已定稿文字的最後 40 字一起收合，抓到跨過定稿邊界的迴圈（`packages/whisper_ggml/ios/Classes/collapse_repetitions.h`、`whisper_flutter_plus.cpp`）；Dart 端在顯示前再收合目前還沒定稿的視窗（`lib/services/repetition.dart`）。沒有打開 fallback，所以不會變慢；代價是迴圈照樣會耗掉那次辨識的時間。

### 二、同一套規則寫兩份，怎麼保證一致

**現象**：Dart 端和 C++ 端各需要一份收合邏輯。

**原因**：whisper_ggml 沒有連結 echo_core，為了幾十行演算法改建置設定不划算。另外，Dart 的 `\p{P}`（Unicode 標點類別）在 C++ 沒有現成的對應，用類別判斷標點，兩邊的結果會不一樣。

**修法**：分隔字元改用明確的字元範圍，兩邊照抄同一組範圍。兩邊的測試都讀同一份 `test/fixtures/repetition_cases.json`；C++ 測試（`packages/whisper_ggml/test_native/`）在 Mac 上用 `clang++` 執行，不用上手機。

### 三、迴圈中間夾一個殘字，會被分成兩段

**現象**：T6 那段「經常」×60 中間夾了一個單獨的「經」，收合後是「經常經經常經」，不是「經常」。

**原因**：殘字打斷了連續重複，所以算成兩個迴圈，各保留一次。

**修法**：不處理。剩下的幾個字不影響閱讀，硬要處理得放寬比對規則，誤判會變多。

### 四、實測時迴圈數都是 0，但預覽明明收合了

**現象**：第一次重播，預覽結尾已經是「經常經經常經」，`[live-metrics]` 的迴圈數卻是 0。

**原因**：那段迴圈出現在最後一個還沒定稿的視窗，是在停止錄音時（`stream_stop()`）收掉的，而這一次收合沒有回報次數。Dart 端拿到的最終文字已經收合過，自己數也是 0。

**修法**：`streamFinal` 帶上 `loops_collapsed`，worker 把它轉成一筆只有次數的 metrics；`LiveRecording` 把它加進總數，但不放進計算延遲中位數的那組資料，以免中位數被拉低。

### 五、「關閉收合」那次其實沒有關

**現象**：兩次重播的 log 都是 `collapse on`，結果一字不差。

**原因**：那次的指令少了 `--dart-define=LIVE_COLLAPSE=false`。另外，`--dart-define` 只在 `flutter run` 時生效，在執行中的 App 按 `R` 重新啟動不會套用新的值。

**修法**：給出兩組完整指令，每組都重新 `flutter run`；log 印出 `collapse on/off`，一眼就能看出設定有沒有生效。

### 六、預覽結尾出現「�」，flutter 印出紅字

**現象**：實際錄音的預覽結尾是「寫��」，flutter 工具印出「Bad UTF-8 encoding」的紅字警告。

**原因**：whisper 把一個中文字拆成兩個 token，最後一次辨識剛好在中間被截斷，只剩半個字的位元組。原生端輸出 JSON 時，本來就會把無效位元組換成 `U+FFFD`（`jsonToChar()`，master 上就是這樣），不是這次改動造成的。

**修法**：收合時一併去掉殘缺的位元組和 `U+FFFD`，Dart 和 C++ 都做，並把實際錄音的結尾加進共用測試資料。

### 七、小坑

- App 裡看不到錄音的檔名，沒辦法指定要重播哪個。重播找不到檔案時，錯誤訊息和 log 會列出所有可以重播的「檔名（錄音名稱）」。
- C++ 字串 `"a\xB8b"` 會被當成一個三位數的十六進位跳脫字元（`\xB8b`），編譯錯誤。改成分開串接：`"a" "\xB8" "b"`。

## 測試方法

- **自動化**：`flutter test` 112 個全部通過，`flutter analyze` 沒有問題；C++ 測試讀同一份測試資料 13 個案例全部和 Dart 一致，另外 4 個原生情境（跨定稿邊界、40 字以外不動、尾端半個字、多餘的延續位元組）也通過；`flutter build ios` 通過。
- **重播對照**：`flutter run --dart-define=LIVE_REPLAY_WAV=<檔名>`，加或不加 `--dart-define=LIVE_COLLAPSE=false`，同一個 build 比較。iPhone 12 Pro Max、debug 模式：

  | 錄音 | 收合 | median total_ms | max lag | 原生收合 | 預覽殘留 |
  |---|---|---|---|---|---|
  | T6 對照組 | 關 | 509 | 1.6 s | 0 | 2 |
  | T6 對照組 | 開 | 521 | 1.6 s | 2 | 0 |
  | 沒有迴圈的錄音 | 關 | 456 | 0.8 s | 0 | 0 |
  | 沒有迴圈的錄音 | 開 | 439 | 0.8 s | 0 | 0 |

  重播很穩定：同一段音訊每次的預覽文字一字不差。
- **實際錄音**：約 3 分半，median 495 ms、max lag 1.2 s，原生收掉 3 個迴圈，預覽沒有殘留。

## 待辦／已知限制

- 長句重複 3 次（例如「我會在這裏拍攝了」×3）低於門檻，不收；之後如果常看到再調整門檻。
- 收合只是把迴圈藏起來；陷入迴圈的那次辨識仍然會一路生到 64 個 token，耗掉的時間沒有省下來。
- 「Helps,…」那種迴圈只有用共用測試資料驗證過，沒找到原始錄音重播。
- Android 沒有實機驗證，原生程式和 iOS 共用。

## 合併說明（2026-10-22）

範圍：整個分支（併入 `master`）

### 改了什麼
- **即時錄音的預覽**：同一段 1～10 個字連續重複 4 次以上（例如「經常經常經常…」），只顯示一次。手機在每 15 秒把預覽文字定稿前先檢查一次，畫面顯示前再檢查一次，兩邊用同一套規則。
- **預覽結尾的「�」**：一個字被截成一半時留下的亂碼，現在會直接拿掉。
- **除錯工具**：開發時可以讓即時錄音改成重播 App 裡已有的錄音，同一段聲音能反覆跑；也可以暫時關掉收合，做前後對照。一般使用者不會碰到。
- 正式逐字稿（停止後重新轉錄的那份）沒有任何改動。

### 怎麼證明能用
- **改動前／後**：同一段 T6 錄音重播，關閉收合時預覽結尾是「經常」連續 60 次，開啟後收成「經常經經常經」，其他文字一字不差（數據表見上方「測試方法」）。
- **速度**：開啟收合的 median 解碼時間 521 ms，關閉時 509 ms（+2.4%），max lag 都是 1.6 秒，遠低於 20% 的門檻。
- **沒有誤收**：沒有迴圈的錄音，開關前後的文字完全一樣。
- **實際錄音**：約 3 分半，收掉 3 個迴圈，預覽沒有殘留，max lag 1.2 秒。
- **自動化測試**：Flutter 112 個測試通過；手機端的 C++ 版和 App 端的 Dart 版讀同一份測試資料，13 個案例結果一致。
- **未驗證**：Android 實機（程式和 iOS 共用）；「Helps,…」那種迴圈只用測試資料驗證過，沒有原始錄音可以重播。

### 出事能不能退回
**雙向門**：預覽文字不會存檔，除錯工具只在開發時用參數打開，`git revert` 就能完全復原。
**影響範圍**：即時錄音預覽——只影響錄音中看到的文字，不影響存下來的錄音和正式逐字稿。
