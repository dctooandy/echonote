## 背景

echonote 是一個會議錄音 App，語音辨識完全在手機上執行，聲音不會上傳。App 裡處理聲音的核心是一個小型程式庫（echo_core）：把聲音轉成辨識引擎要的格式、計算音量、畫波形、判斷有沒有人在說話。這個程式庫公開在 GitHub 上。

前三週，我用 C 語言寫了這個程式庫，並讓三種語言都能直接使用它：Flutter（App 本身）、iOS 的 Swift、Android 的 Kotlin。一份程式庫給多種語言使用時，每一種語言都需要一層「轉接」（業界叫 binding 或 wrapper）。這一天的工作是為了應徵一個「跨平台 SDK 工程師」職缺：對方的工作是把 C/C++ 程式庫提供給 Windows、.NET 等平台使用，並負責打包與發版。這三件事我原本都沒有做過，所以連續做了三個分支來補上。

## 本次目標

- **A. 第四種語言：C#**：讓 Windows 與 .NET 的主要語言 C# 也能直接使用同一份程式庫（這種機制叫 P/Invoke），並在 Windows、macOS、Linux 三種電腦上自動測試。
- **B. 程式庫內部改用 C++**：把程式庫內部從 C 改成 C++，但對外的介面一個字都不改，四種語言的轉接也都不用改。這是 SDK 公司最常見的做法：內部用 C++ 寫，對外只提供 C 的介面。
- **C. 像正式產品一樣發版**：有版本號和「什麼改動要升哪一位」的規則；打包成 .NET 開發者能直接安裝的套件；推一個版本標籤，電腦就自動測試、打包、在乾淨的環境驗證、發佈，任何一步失敗就不發佈。

## 問題與修正

每個問題都分成三部分：看到什麼（現象）、為什麼（原因）、怎麼解決（修正）。

### 一、開發環境

#### 1. 安裝 .NET 開發工具需要管理員密碼

**現象**：用平常的安裝方式（Homebrew）安裝 .NET 開發工具時失敗，系統要求輸入管理員密碼。

**原因**：這個安裝程式必須用管理員權限執行，而 AI 開發助手的指令視窗不能輸入密碼。

**修正**：改用微軟官方提供的安裝腳本，裝在使用者自己的資料夾，不需要管理員權限。編譯工具 CMake 則照常用 Homebrew 安裝。

#### 2. 建立測試用的 C# 專案時失敗

**現象**：在本機驗證安裝套件時，用指令自動建立一個新的 C# 專案，指令失敗。

**原因**：原因待查。目前只推測是新版開發工具的專案範本，不接受我們指定的 .NET 8 版本。

**修正**：改成手寫專案設定檔。自動化流程裡驗證套件的步驟，也一樣用手寫的設定檔。

### 二、程式庫內部改用 C++

#### 3. Flutter 的建置腳本不知道現在是在編哪個平台

**現象**：修改 Flutter 的建置腳本後，檢查工具回報錯誤，說找不到「目標平台」這個欄位。

**原因**：這個欄位是由另一個套件（code_assets）提供的，建置腳本沒有引用那個套件。

**修正**：在建置腳本裡加上引用，再用它判斷目前是不是在編 Android 版。

#### 4. iOS 的套件工具把 C++ 檔案當成 C 來讀

**現象**：iOS 這邊的測試無法編譯，錯誤是找不到 C++ 才有的標準檔案。

**原因**：iOS 的套件工具（SwiftPM）預設會把資料夾裡所有的介面檔都公開給 Swift，包括只有 C++ 能讀的內部檔案，Swift 只會用 C 的規則去讀，所以失敗。

**修正**：加一個設定檔（`module.modulemap`），明確指定只公開 C 的介面檔。

#### 5. Android 版把內部的程式名稱也公開了

**現象**：改成 C++ 之後，檢查 Android 版程式庫對外公開的名稱，除了應該公開的 8 個函式，還多了程式庫內部的 5 個函式，以及 70 多個屬於 C++ 標準函式庫的名稱。

**原因**：Flutter 的建置工具預設會公開所有名稱；被打包進來的 C++ 標準函式庫，它的名稱也跟著公開了。同一個 App 裡，語音辨識引擎（whisper）也帶了自己的一份 C++ 標準函式庫。兩邊公開同樣的名稱，系統載入時可能把兩邊混在一起用。

**修正**：在建置設定裡指定「預設不公開」，並把 C++ 標準函式庫的名稱留在程式庫內部。修正後只公開 8 個函式。

#### 6. Android 版程式庫大了 37 倍，原因不是大家以為的那個

**現象**：改成 C++ 之後，Android 版程式庫從 5,816 bytes 變成 214,744 bytes，大了約 37 倍。

**原因**：C++ 程式庫變大，一般會先懷疑「例外處理」。我另外用 Android 的編譯工具單獨編譯三個版本比較：原本的寫法 214,160 bytes；關掉例外處理 214,248 bytes，幾乎沒變；改用 C 語言的方式配置記憶體（`malloc`）5,432 bytes。所以真正的原因是 C++ 配置記憶體的方式（`operator new`）：只要用到它，整套 C++ 標準函式庫的執行部分就會一起被打包進來。

**修正**：程式庫唯一需要配置記憶體的地方，改用 C 語言的方式配置，再在那塊記憶體上建立 C++ 物件。程式庫內部也不再使用任何會配置記憶體或會丟出例外的 C++ 功能。Android 版回到 5,832 bytes，跟 C 版幾乎一樣。這也代表程式庫的錯誤不可能以「例外」的形式跑到 Flutter、Swift、Kotlin、C# 那一邊。

#### 7. Android 預設的 C++ 標準函式庫連結方式會讓 App 打不開

**現象**：寫規格時，我讀了 Flutter 建置工具的原始碼，發現 Android 預設使用「共用版」的 C++ 標準函式庫。這是事先發現的，沒有實際發生錯誤。

**原因**：共用版需要另外把一個檔案（`libc++_shared.so`）放進 App，Flutter 的建置工具不會自動放。

**修正**：改成「打包進程式庫」的版本（`c++_static`），跟語音辨識引擎的設定一致。檢查後確認程式庫只依賴 Android 系統本來就有的檔案。

### 三、發版流程

#### 8. 套件裡的檔案位置多了一層

**現象**：第一次在本機打包 .NET 套件，Mac 版程式庫被放在重複兩次的資料夾路徑裡。

**原因**：打包工具會自動加上子資料夾的路徑，而我在設定裡又自己加了一次。

**修正**：拿掉自己加的那一段。修正後，用一個全新的 C# 專案安裝這個套件並執行，正確印出版本 0.2.0 與音量 0.5。

#### 9. Windows 自動化環境的兩個差異，事先處理

**現象**：沒有實際發生，是寫自動化流程時事先處理的：Windows 的自動化環境沒有 `python3` 這個指令名稱，只有 `python`；Windows 程式輸出的每一行結尾多一個看不見的字元，直接比對文字會失敗。

**修正**：依作業系統選擇指令名稱；比對前先去掉那個字元。自動化流程第一次執行就全部通過。

#### 10. 同步到公開版本時，把授權條款蓋掉了

**現象**：把 App 裡的程式庫整批複製到公開的 GitHub 專案後，開源授權條款（MIT）變回了範本裡的空白內容，套件說明也變回舊版。

**原因**：公開專案第一次建立時，這兩個檔案是在公開專案那邊修改的，App 裡的原始版本沒有跟著改。

**修正**：在公開專案改回來，並把 App 裡的兩個檔案改成一致，之後整批複製就不會再蓋掉。

#### 11. 大小比較表混用了兩種量法

**現象**：寫這份紀錄時重新核對數字，發現說明文件的大小比較表裡，有一個數字是 Flutter 建置工具的產物，另一個是單獨編譯的結果，卻放在同一欄比較。

**修正**：把表格拆成兩欄，各自註明量法，並說明只比較同一欄裡的數字。結論不變。

## 怎麼驗證

- **程式庫改成 C++ 之後，計算結果完全不變**：Flutter 這邊的 21 項自動測試全部通過，其中包括和另一份純 Dart 寫的參考程式逐位元比對結果。
- **四種語言都正常**：Swift 7 項、C# 10 項、Kotlin 5 項（在 Android 模擬器上）自動測試全部通過；iPhone 模擬器與 Android 模擬器上的 App 也都能載入並執行程式庫。
- **只公開該公開的名稱**：每個平台的程式庫都只公開清單上的 9 個函式（原本 8 個，加上這次新增的「查詢版本」），自動化流程每次都會檢查。Windows 版是直接讀取程式庫檔案的內部結構來檢查，不需要額外安裝工具。
- **每次修改都自動測試**：GitHub 上的自動化流程有 7 項工作，包含 Flutter（Mac、Linux）、Swift、C#（Windows、Mac、Linux）與版本號檢查，第一次執行就全部通過。
- **發版流程從頭到尾跑過兩次**：先用試用版（0.2.0-rc.1），再用正式版（0.2.0）。每次 19 項工作全部通過：5 種平台的程式庫各自編譯並檢查處理器架構、打包並確認 5 個程式庫都在、在 Windows、Mac、Linux（兩種處理器）各建一個全新的專案安裝套件並執行，最後建立 GitHub 發佈頁面並上傳套件。
- **大小**：Android 版程式庫從 5,816 改成 5,832 bytes；Mac 版從 33,808 改成 34,064 bytes。

## 已知限制

- Intel Mac 版是在 Apple 晶片的電腦上編譯的，自動化流程只確認編譯成功、處理器架構正確，沒有實際執行過。
- 放在 GitHub Packages 的套件，即使是公開的，使用者也要先登入 GitHub 才能安裝；不需要登入的下載方式是 GitHub 發佈頁面上的套件檔。
- 程式庫內部不能使用會配置記憶體的 C++ 標準容器，否則 Android 版又會變大。
- Windows 版的計算結果不要求跟其他平台逐位元相同，測試只比對已知的正確值。
- 不支援 Windows 的 ARM 電腦與 32 位元系統；Android 只支援 64 位元 ARM 處理器。
