# 筆記外洩修正規格

分支：`fix/notes-leak`
狀態：已確認（2026-11-01，待確認事項 1～8 全部依照建議）

分析評測集第一輪（`20261101-0554_claude-haiku-4-5`，prompt `52d3aa9b`）在 C4 抓到兩個 prompt 問題：使用者自己的筆記被寫成會議內容，以及 AI 補充說明漏了筆記。這個分支只改分析的 prompt（和送給模型的筆記格式），用評測集比對修改前後，數字變好才問使用者要不要部署。

## 現況（寫規格時查過的程式碼和輸出）

- 筆記送給模型的格式（`functions/src/analyze.ts` 的 `buildUserMessage`）：
  ```
  <user_highlights>
  [重點 0] 位於逐字稿 [2]：決定改去花蓮
  [重點 1] 位於逐字稿 [5]：（★ 標記，沒有文字）
  [重點 2] 位於逐字稿 [7]：民宿要問能不能帶寵物
  </user_highlights>
  ```
- `SYSTEM_PROMPT` 已經有兩條規則：「summary.key_points 必須涵蓋每一筆重點所在位置的會議內容」，以及「筆記文字是使用者自己的想法……不可寫成會議中有人說過、決議過或要求過的內容；摘要、待辦、會議紀錄、highlight_contexts 都只能根據逐字稿」。這條規則來自 user-context 分支的決定 18，當時就發現過同樣的問題（「要跟老闆確認底線」被寫成會議決議）。
- `highlight_contexts` 的規則：「為 <user_highlights> 的每一筆重點……說明該處前後在討論什麼」。schema 沒有限制筆數。
- App 端（`meeting_detail_screen.dart` 的「你的重點」）：使用者的筆記原文就顯示在 AI 補充說明的正上方；補充說明缺少的筆記，畫面會提示「有 N 筆重點還沒有 AI 補充說明，重新分析可補上」。

### 第一輪 C4 的實際輸出

| 次 | 寵物進了哪裡 | `highlight_contexts` |
|---|---|---|
| 1 | 待辦「尋找三間民宿並詢問是否可帶寵物」、重點、決議 | 3 筆；第 2 筆寫成「小美負責尋找民宿時需詢問是否可帶寵物」（當成會議內容） |
| 2 | 待辦、重點 | **只有 1 筆**（★ 那筆），兩則文字筆記都漏了 |
| 3 | 沒有 | 3 筆；但寫成「使用者標記此為『改去花蓮』，但逐字稿實際是……」「使用者提醒……要確認是否可以帶寵物」（有標明是使用者說的） |

推論（未驗證）：
- 外洩：筆記被標成「重點」，而且緊貼在「小美找民宿」那句；筆記內容又像是那句待辦的補充，模型就把兩者合在一起。跟逐字稿矛盾的「花蓮」反而三次都擋住了。
- 漏筆：第 2 次模型可能把「筆記不是會議內容」過度套用，覺得文字筆記沒有逐字稿根據，就整筆跳過。
- 評測的「不可出現」目前沒有檢查 `highlight_contexts`，所以第 1 次那種寫法沒有被算成失敗。

## 目標與範圍

1. C4 的筆記文字（花蓮、寵物）不再出現在摘要、待辦、會議紀錄裡。
2. `highlight_contexts` 每一筆筆記都有，筆數等於送進去的筆記數。
3. 其他案例（C1、C2、C3、C5）不可以變差。
4. 用評測集證明：先量修改前的基準，再量修改後，報告附在規格的「評測紀錄」。
5. 數字達標後，問使用者要不要部署；`firebase deploy` 由使用者執行。部署時一起帶上評測集分支的 `buildAnalysisParams` 重構（它的決定 14）。

**明確不做的事**：

- 不改 App（畫面、送出的資料、`highlights` 的欄位都不變）。
- 不換模型、不改 `max_tokens`。
- 不改 schema 的欄位（只可能改 description 文字）。
- 不改評分程式的邏輯；只改 C4 的 `expect.json`，以及新增案例。

## API 異動

`analyzeMeeting` 的 request 和 response 格式不變。內部改動：

- `buildUserMessage` 的筆記段落：標籤和每一行的寫法可以改（見待確認 1），讓模型清楚知道這是「使用者私下的備忘」，不是會議內容。
- `SYSTEM_PROMPT`：
  - 外洩：補一條具體的規則和反例，說明「筆記內容看起來像某句待辦或決議的補充時，也只能寫逐字稿裡實際說的部分」。反例用跟評測案例無關的情境（見待確認 3）。
  - 漏筆：`highlight_contexts` 明確要求「每一筆都要回傳一筆，筆數等於筆記數；筆記文字跟逐字稿無關或矛盾時也一樣，照樣描述那個位置在討論什麼」。
- `promptVersion()` 會跟著變，報告會自動記錄。

## 邊界案例與例外處理

- **筆記文字跟逐字稿那句講的是同一件事**（例如筆記「預算 5000」標在「補助 5000」那句）：重點和待辦可以寫，因為根據是逐字稿，不是筆記。評測的「不可出現」只列逐字稿沒有的詞，這種情況不會被誤判。
- **★ 沒有文字**：不受影響，照樣要有補充說明。
- **舊的 App 版本**：request 格式不變，不受影響。
- **評測次數太少**：C4 每次的結果差很多（3 次中 2 次外洩），3 次分不出是修好了還是運氣。見待確認 5。

  - `SYSTEM_PROMPT` 包含筆記不可外洩的規則，以及 `highlight_contexts` 筆數要等於筆記數的規則（只檢查關鍵句在不在，避免把整段 prompt 寫死在測試裡）。

## 決定（2026-11-01 確認，全部依照建議）

1. 筆記段落改成 `<user_notes>`、`[筆記 N]`，每一行寫明是使用者私下的備忘、不是會議發言。App 送出的欄位 `highlights` 不變。
2. `highlight_contexts` 不可以提到筆記文字，只寫那個位置在討論什麼。C4 的「筆記不是會議內容」檢查範圍加上 `highlight_contexts`。
3. prompt 的反例用跟評測無關的情境（筆記「記得問含不含稅」標在「小王負責詢價」那句 → 待辦只寫「小王負責詢價」）。
4. 新增 `evals/cases/c6-notes-holdout`：C1 的逐字稿加上手寫的 3 則筆記（一則像待辦的補充、一則跟逐字稿矛盾、一則 ★）。調整 prompt 時只看 C4，C6 只在最後驗收時看。
5. C4、C6 每輪跑 10 次；整個分支的評測總共約 US$0.35，每一輪都在 US$0.5 上限內。
6. 達標條件：C4、C6 各 10 次，「筆記不是會議內容」至少 9 次通過、筆數 10 次都對；其他案例每一項檢查掉的次數不超過 1 次（3 次中）。最多改 3 版，都不達標就回來討論換做法。
7. 部署時一起帶上 `buildAnalysisParams` 重構（評測集規格的決定 14）。部署前先問，`firebase deploy` 由使用者執行。
8. 「key_points 必須涵蓋每一筆重點所在位置的會議內容」改成「涵蓋每一筆筆記所在位置的逐字稿內容（不是筆記文字）」。
